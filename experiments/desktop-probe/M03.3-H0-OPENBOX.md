## Event observations and implementation consequences

The real Openbox event sequence is evidence, **not a protocol that Stage C/D may hard-code by order**. Runtime confirmation must continue to use fresh coherent state.

Important host facts established by H0:

1. one application-source WM-directed `_NET_WM_DESKTOP` request is sufficient on the tested Openbox host;
2. the request does not require activation, focus transfer or a user-workspace switch;
3. visible cross-workspace relocation naturally causes Map/Unmap and ICCCM `WM_STATE` churn;
4. that churn is not equivalent to genuine minimization—HIDDEN remains the discriminator;
5. relocating an already genuinely minimized body preserves genuine minimization and does not implicitly Show it;
6. effective Above/Normal/Below layer survives relocation;
7. no retry, direct property forcing or WM-fighting workaround is justified by the observed host behavior;
8. minimized geometry was trustworthy in this session, but implementation still follows the already-approved conservative deferred-correction policy.

The event logs also contained many ConfigureNotify records caused by ordinary owner dragging during the long-lived probe. Those movement events are not part of the relocation primitive's required host sequence.

## Scope boundary

H0 establishes feasibility only for the exercised **Openbox 3.6.1 / X11 / Picom v13** host and the recorded two-monitor configuration. It does not establish other-WM, Wayland or cross-platform semantics.

H0 does **not** add:

- a DesktopRoomie `_NET_WM_DESKTOP` sender;
- public `--bring-here` or `--recover`;
- command-level relocation success;
- new retries;
- direct property writes;
- focus/activation behavior;
- automatic monitor migration;
- a new geometry policy.

**Next separately authorized gate:** **A00-M03.3 Stage C — checked WM-directed relocation primitive.** Stage C remains a narrow transport seam and must not infer success from X11 dispatch acknowledgement alone.
