PROJECT VANILLA
ALL IDEAS / DESIGN INVENTORY
Version 0.1
Date: 2026-10-04

STATUS
======

This is NOT a roadmap, priority list, commitment, or final architecture.

It is an idea inventory: a consolidated record of the concepts, design directions,
experiments, possible systems, workflows, constraints, and examples that have come up
throughout the Project Vanilla discussions so far.

Some ideas overlap. Some are alternatives. Some may later be rejected. Some have already
been partially implemented. The purpose here is to preserve the design space before
turning it into a serious roadmap.

The central rule for reading this document is:

    "An idea being listed here does not mean the project has decided to build it."

======================================================================
1. CORE VISION
======================================================================

Project Vanilla is not intended to be "a chatbot with a Vanilla skin."

The larger idea is a persistent character simulation in which Vanilla gradually feels
like a character who exists continuously across devices and contexts.

Ideas discussed for that experience include:

- Vanilla continues to have state when the user is not actively talking to her.
- She has physiological needs, mood, activities, habits, memories, routines and a
  relationship history.
- She can be observed doing things rather than always waiting for a prompt.
- She can refuse, delay, ignore, sleep, get distracted, become annoyed, approach,
  retreat, or otherwise behave without needing to speak.
- Her state should explain behavior: a response should feel like a consequence of what
  happened before rather than an isolated generated message.
- The long-term illusion is continuity, not merely intelligence.
- A useful north star is:
      "Vanilla has been here long enough that what she is doing now makes sense because
       of things that happened before."

The project has also been imagined as having two layers:

1. A private Project Vanilla implementation using the copyrighted NEKOPARA character,
   assets and corpus owned by the user.
2. A later public/general engine that is character-agnostic, with the simulation,
   renderer, services and schemas separated from private character packs/assets.

======================================================================
2. "ONE VANILLA, MANY BODIES"
======================================================================

A repeated architectural idea is that there should never be independent copies such as:

- "desktop Vanilla"
- "phone Vanilla"
- "chat Vanilla"

Instead, there is one persistent Vanilla identity/state with multiple bodies/interfaces.

Possible bodies/interfaces discussed:

- Linux desktop companion
- Android room/body
- Android messages
- Android notifications
- voice-message interface
- future debug/web panel
- future external integrations
- possibly other device frontends later

Long-term conceptual model:

    VANILLA CORE
        |
        +-- Linux desktop body
        +-- Android body / room
        +-- messages / notifications
        +-- TTS service
        +-- LLM service
        +-- image service
        +-- future integrations

One long-term idea is for a phone to become the authoritative always-available Vanilla
Core, with the desktop becoming a connected body rather than the source of identity.

A different near-term reality is that the Arch Linux machine remains the main
development host. The question of which physical device ultimately owns authoritative
state is intentionally open until battery, Android background execution, storage,
reliability and synchronization behavior are tested.

======================================================================
4. THE LLM SHOULD NOT OWN VANILLA
======================================================================

A foundational design idea is to make the LLM a cognitive/language tool, not the
persistent character database.

The simulation should own durable truth such as:

- needs
- current mood state
- relationship state
- routines
- activities
- event history
- memory records
- world state
- known places
- cooldowns
- permissions
- recent behavior
- persistent summaries

Possible LLM jobs:

- interpret user language
- propose semantic meanings/events
- create novel dialogue
- summarize memories
- reason over structured state
- generate offline dialogue candidates
- help produce character-consistent content

The LLM should not be able to arbitrarily rewrite persistent emotional state or memory
simply because a generated answer says something happened.

An important distinction is:

    simulation decides what is true
    senses decide what Vanilla observed
    Brain decides what Vanilla believes
    memory decides what remains available later
    LLM helps reason/speak about the structured result

======================================================================
5. GROUND TRUTH != OBSERVATION != BELIEF != MEMORY
======================================================================

A more detailed cognitive architecture idea was developed around epistemic separation.

The computer can know something that Vanilla does not know.

Suggested layers:

GROUND TRUTH
- actual simulation/world state
- exact time
- exact device state
- exact location category
- actual event occurrence

OBSERVATION
- what a sensor reported
- may be incomplete
- may be uncertain
- may be noisy
- may be stale
- has source and timestamp

BELIEF
- Brain's current interpretation of observations
- has confidence
- may be wrong
- may be revised when better observations arrive

MEMORY
- retained representation of earlier experiences/beliefs/events
- can be summarized or consolidated
- does not necessarily equal current truth

METACOGNITION
- Vanilla may have different certainty levels about what she knows
- "I think..."
- "I'm not sure..."
- surprise when a reliable observation contradicts an earlier belief

Example idea:

Vanilla sleeps.

Her internal/subjective sense of time suggests she slept about an hour.

A reliable clock observation after waking says time went from 07:21 to 14:37.

The Brain revises its belief and may react:

    "I slept seven hours?!"

The important part is not the line itself; it is that the surprise comes from a belief
update rather than a scripted time check.

======================================================================
6. UNCERTAIN / PROBABILISTIC SENSES
======================================================================

Senses were imagined as producing perceptions with uncertainty rather than omniscient
facts.

Possible observation fields:

- value
- confidence
- source
- timestamp
- freshness
- uncertainty
- optional competing interpretation

Examples:

- sound direction is probably to the left
- user appears to be near
- unfamiliar place scent has low familiarity
- internal estimate says "a while has passed"
- a sensor has not updated because Vanilla was asleep

This opens the possibility of believable mistakes, stale beliefs, uncertainty and
revision.

It also preserves the principle:

    computer-available information != Vanilla-known information

======================================================================
7. NERVOUS SYSTEM / SPINE / REFLEX ARCHITECTURE
======================================================================

A major idea was to add a nervous "highway" between senses, body and Brain.

Concept:

    sensors
       |
       v
      SPINE
       | \
       |  \-- fast body/reflex response
       |
       +---- escalation to Brain when appropriate

The Spine can:

- route typed sensory signals
- perform reflexes
- control immediate body reactions
- decide whether/when to wake or escalate to conscious processing
- allow the body to respond without forcing an LLM/Brain cycle

Example: lifting Vanilla while she sleeps

    body/proprioception detects movement
        ->
    Spine/body curls, shifts, twitches, clings or mumbles
        ->
    Brain may remain asleep
        ->
    event may never enter conscious memory

Example: thunder while sleeping

    ears detect sudden loud sound
        ->
    Spine produces immediate startle / ear movement / body contraction
        ->
    a slower escalation signal may wake the Brain
        ->
    conscious interpretation happens after the reflex

This architecture is meant to make the body feel alive even when conscious cognition is
inactive.

It also suggests future autonomic systems such as:

- startle
- balance
- posture
- protective movement
- sleep reflexes
- arousal/wake thresholds
- instinctive reactions

======================================================================
8. SLEEP AS AN ACTUAL SYSTEM STATE
======================================================================

Sleep was discussed as more than an animation.

Possible consequences of sleep:

- eyes may stop producing observations
- some senses may become reduced rather than fully disabled
- beliefs about the world can become stale
- body/spine reflexes can still function
- loud/important signals can cross a wake threshold
- normal events may be ignored
- events processed only by reflexes may never be encoded as conscious memory
- waking may trigger requests for fresh observations
- subjective time and actual time can diverge

Future environmental systems such as thunder/weather could interact with this layered
sleep model.

======================================================================
9. MEMORY IDEAS
======================================================================

Several compatible memory taxonomies have been discussed; they are not yet reconciled
into one final design.

One proposed brain-oriented hierarchy:

- instant memory
- short-term memory
- mid-term memory
- long-term memory

Another proposed functional hierarchy:

IMMEDIATE MEMORY
- minutes/hours
- current conversation/activity context

EPISODIC MEMORY
- specific noteworthy events

SEMANTIC MEMORY
- stable learned facts/preferences

EMOTIONAL ASSOCIATIONS
- patterns that influence responses without necessarily becoming explicit prose memories

Other memory ideas:

- summaries rather than storing/reinjecting entire conversation logs
- memory importance
- memory consolidation
- forgetting/decay
- retrieval by current context
- source/confidence metadata
- events that affect behavior even when not explicitly recalled
- memory should remain simulation-owned rather than living only in LLM context

======================================================================
10. RELATIONSHIP MODEL
======================================================================

Relationship state was imagined as slow-moving and separate from momentary mood.

Possible slow variables:

- familiarity
- trust
- attachment
- comfort
- conflict residue

Possible design rule:

    mood changes over minutes/hours
    relationship changes over weeks/months

This prevents a single annoyed moment from rewriting a long-established relationship.

The long-term idea is that a six-month relationship should feel different from week one
even if the current mood happens to be similar.

12. EMOTIONS / MOOD
======================================================================

Possible continuous state variables discussed:

- valence / happiness
- irritation
- affection
- anxiety
- playfulness
- sociability
- concern
- curiosity

Possible transient named states:

- sleepy
- excited
- sulking
- embarrassed
- lonely
- annoyed
- worried

Emotional dynamics ideas:

- inertia
- bounded stochastic drift
- event impulses
- recovery
- hysteresis
- cross-variable interaction
- personality-dependent responses

The goal is to avoid mechanical logic such as:

    hunger >= 75 -> play complaint #12

Instead, the same event can have different effects based on current state and history.

Mood should also not directly map to one TTS emotion label. It can be a prior that helps
select the desired delivery.

Example:

    state:
        irritation high
        affection high
        energy low

    event:
        user apologizes

    possible delivery:
        still sulking
        quiet
        restrained
        slightly softened

13. BEHAVIOR SELECTION / AGENCY

Potential inputs:

- needs
- mood
- personality
- current activity
- environment
- time
- relationship
- recent actions
- cooldowns
- user presence
- randomness

Output:

- selected behavior/activity

A developer-only explanation/debug view was proposed so strange behavior can be traced.

Example:

    Behavior: refuse_play
    tiredness > 80       +0.41
    irritation > 55      +0.19
    played recently      +0.12
    affection            -0.08
    final score           0.64

The desired result is behavior with understandable causes that is still not fully
predictable.

19. OFFLINE/PRE-GENERATED DIALOGUE FIRST
======================================================================

A major design direction is to avoid generating every ambient line live.

Most ordinary ambient dialogue could come from a large local pre-generated library.

Advantages considered:

- zero network latency
- predictable characterization
- no cloud/API dependency
- immediate playback
- quality can be reviewed before use
- reused dialogue costs nothing
- known lines can have prerecorded/generated voice ready

Live LLM + TTS can be reserved for:

- direct conversations
- genuinely novel circumstances
- unique messages
- rare combinations of context
- lines that can later be reviewed and promoted into the permanent library

23. SEMANTIC EVENT INTERPRETER
======================================================================

A possible role for the LLM is to translate free language into structured semantic
events.

Example:

    {
      rejection: 0.78,
      insult: 0.31,
      playful_tone: 0.42,
      user_affect: irritated
    }

Vanilla Core, not the LLM, then determines the emotional/relationship consequences.

This could let identical words cause different reactions depending on history/state.

41. CORPUS AS A FOUNDATIONAL ASSET
======================================================================

One of the highest-value early ideas was to recover exact script-to-voice relationships
from NEKOPARA data rather than transcribing voices with STT.

General pipeline:

    extracted scenario/script data
        +
    voice/audio assets
        ->
    engine-specific parsers
        ->
    exact speaker + Japanese text + voice reference
        ->
    canonical corpus

This became a major implemented direction, but its design ideas remain important:

- source text is authoritative when recoverable
- no Whisper/STT as primary mapper
- raw source fields are preserved
- normalized fields are separate
- full dialogue sequence/context is preserved before character filtering
- paths are portable/root-relative
- audio identity is resolved conservatively
- ambiguous/missing assets stay explicit
- no silent substitution
- adult provenance is explicit
- multi-speaker/multi-voice material stays canonical even when unusable for clean TTS

Engine adapters:

- CatSystem2 for Vol.3
- KiriKiri/FreeMote-derived data for the other games

The general architectural lesson is:

    engine-specific import adapters
        ->
    one shared canonical schema

- expression
- pose
- BGM/SFX context
- quality/audit metadata
- emotional annotations later

The rich corpus is intended to support more than TTS:

- style study
- Character Bible construction
- emotion analysis
- contextual dialogue examples
- relationship analysis
- multi-character interaction research
- reference retrieval
- future animation/expression alignment

======================================================================
43. SOURCE IMMUTABILITY / PROVENANCE
======================================================================

A persistent data-engineering principle:

- extracted originals stay immutable/read-only
- repairs happen on explicit copies
- raw fields stay preserved
- normalized interpretations are separate
- known anomalies remain auditable
- source paths/provenance are retained
- no guessed speaker/audio substitutions
- no destructive cleanup merely to make reports look clean

This matters because future models may need information that an early exporter considered
irrelevant.

======================================================================
44. TTS DATA SHOULD HAVE MULTIPLE USES
======================================================================

The curated Vanilla audio work introduced explicit use categories rather than one binary
"training/not training" decision.

Possible/implemented uses:

SPEECH
- material allowed into speech TTS fine-tuning

REFERENCE
- material suitable as a voice/style reference

REACTION
- nonverbal/onomatopoeic/useful companion sound that may be directly played

One clip can potentially have multiple uses.

Derivatives can have different uses from the original source.

Concrete design example:

- one source contains spoken material plus sniffing/onomatopoeia
- split into separate derivatives
- speech portion can serve speech/reference
- nonverbal portion becomes reaction-only
- neither useful portion needs to be thrown away

This is intended to preserve valuable character performance rather than optimizing only
for conventional TTS.

======================================================================
45. EXPRESSIVE AUDIO SHOULD NOT BE AUTOMATICALLY DISCARDED
======================================================================

Potentially valuable categories include:

- sleepy speech
- happy speech
- annoyed speech
- excited speech
- soft speech
- whispered/quiet delivery
- dramatic pauses
- laughter embedded in spoken lines
- nonverbal reactions
- onomatopoeia

The project wants expressive range, so a "perfect neutral studio voice only" filter could
destroy exactly the material later needed for emotional TTS.

======================================================================
46. LONG PAUSES / SILENCE POLICY IDEA
======================================================================

Silence has different meanings.

Leading silence:
- generally safe to trim later
- should not automatically reject a clip

Trailing silence:
- generally safe to trim later
- should not automatically reject a clip

Internal silence:
- may be real prosody
- may be dramatic delivery
- may be engine/runtime gap
- may represent two utterances
- should not be removed blindly

Possible audit measurements:

- duration
- leading silence
- trailing silence
- longest internal silence
- internal silence count
- total silence
- silence ratio
- RMS
- peak
- clipping
- non-silent region count

The philosophy is distribution-first:

    measure first
    inspect outliers
    choose thresholds from real data
    do not impose arbitrary universal TTS thresholds

======================================================================
47. HUMAN REVIEW TOOLING
======================================================================

The corpus workflow also inspired the idea of a local review GUI/reporting system.

Useful review features:

- play audio

- Japanese text
- localization/context
- previous/next lines
- pause metrics
- excerpt/split decisions
- explicit uses: speech/reference/reaction
- tags
- revision history
- manual overrides
- per-excerpt decisions
- sortable suspiciousness
- export/review reports

A core policy discussed:

    unflagged material is provisionally usable
    explicit/manual decisions override automatic policy

48. TTS MODEL OPTIONS THAT WERE CONSIDERED
======================================================================

Several Japanese voice-cloning/TTS approaches were discussed as candidates rather than
all being committed choices:

GPT-SoVITS
- strong fit for Japanese
- zero-shot voice cloning
- fine-tuning
- reference-conditioned delivery
- multiple model generations considered

GPT-SoVITS v5
- considered especially for strong zero-shot speaker similarity
- not the main fine-tune path discussed

GPT-SoVITS v2Pro / v2ProPlus
- attractive for fine-tuning
- considered more forgiving of game/compressed audio
- v2ProPlus became the first concrete experiment candidate

GPT-SoVITS v4
- considered as a possible higher-quality experiment if source audio quality supports it

Fish Audio S2
- discussed as a strong zero-shot challenger

CosyVoice
- discussed as another modern multilingual/Japanese option

XTTS-v2
- discussed as a mature baseline/control rather than necessarily the final choice

General model-selection idea:

    zero-shot bake-off first
    fine-tune only if fine-tuning improves actual results

49. TTS SHOULD BE REFERENCE-CONDITIONED / STYLE-AWARE

Possible references:

This can preserve performance diversity even after speaker fine-tuning.

======================================================================
52. CURRENT FIRST TRAINING EXPERIMENT IDEA
======================================================================

One concrete first-training design was developed around GPT-SoVITS v2ProPlus.

Model-specific package ideas:

- portable audio directory
- train list
- holdout list
- reference manifest
- reaction manifest
- checksums
- package verifier
- helper to turn relative paths into machine-specific absolute lists
- original Japanese model transcripts
- no ASR

Current first package context:

- approximately 1,400 model-usable speech clips
- deterministic 60-clip holdout
- approximately 1,340 training clips
- roughly 5,963 seconds of train audio
- 12 fixed references
- reaction material kept separate

These numbers are implementation state, not a universal design requirement.

======================================================================
53. TRAINING AS CONTROLLED EXPERIMENT
======================================================================

Training was framed as an experiment rather than "train until latest epoch and accept it."

Ideas:

- zero-shot baseline first
- short smoke training
- periodic checkpoints
- fixed Japanese test sentences
- fixed reference clips
- same inference settings across comparisons
- compare speaker similarity, pronunciation, stability, artifacts, pacing and expressive
  range
- latest checkpoint is not automatically best

First discussed v2ProPlus schedule:

SMOKE
- SoVITS 2 epochs
- GPT 3 epochs

MAIN
- SoVITS 8 epochs
- save at roughly 4/8
- GPT 15 epochs
- save at roughly 5/10/15

Comparison grid idea:

- S4 + G5
- S4 + G10
- S4 + G15
- S8 + G5
- S8 + G10
- S8 + G15

Possible outcomes:

- fine-tune clearly improves Vanilla -> keep it
- zero-shot is already better -> keep references, skip needless training
- identity improves but expression collapses -> earlier checkpoint / less training
- identity remains insufficient -> compare another model rather than blindly sweeping
  hyperparameters

======================================================================
54. BURST CLOUD TRAINING
======================================================================

Cloud compute was imagined as burst capacity rather than a permanent dependency.

AWS training idea:

- private S3 staging bucket
- encrypted storage
- GPU EC2 rented only for the experiment
- g5.xlarge / A10G class machine as first candidate
- private SSH access
- no public Gradio ports
- pinned GPT-SoVITS commit
- train
- upload checkpoints/results
- download/verify locally
- terminate instance

General principle:

    cloud can accelerate training
    cloud should not become the authoritative source of Vanilla's identity/state

======================================================================
58. COLAB IS NOT AN ALWAYS-ON SERVER
======================================================================

A specific architectural caution:

Colab can be useful for:

- batch generation
- occasional on-demand generation
- checkpoint testing
- cloud inference experiments
- building speech libraries

But the final live companion should not depend on Colab responding with low latency 24/7.

Possible long-term hierarchy:

FAST PATH
- local inference on RTX 3050 if practical

CLOUD/BATCH PATH
- Colab or another temporary GPU for expensive/batch jobs

The local-inference capability should be measured after training because inference is
much cheaper than training.

======================================================================

- TTS model
- image generator
- cloud service
- device

        ->

======================================================================
71. "SYSTEM KNOWS MORE THAN VANILLA" AS A GENERAL PRINCIPLE
======================================================================

This principle applies beyond sensors.

Examples:

- system knows exact clock; Vanilla has subjective time
- system knows precise coordinate; Vanilla knows a scent/familiarity abstraction
- system knows internal utility scores; Vanilla experiences an urge/refusal
- system knows why an event was generated; Vanilla experiences it as part of her world
- system knows hidden rare-event triggers; Vanilla does not
- system knows image-generation implementation; Vanilla experiences a photo/gallery
- system knows a message queue exists; Vanilla experiences sending/receiving messages

This supports immersion without requiring the character to be modeled as omniscient.

LLMs/cloud services are accelerators for richness, not the heartbeat of Vanilla.

======================================================================
75. FINAL NOTE
======================================================================

The recurring idea behind Project Vanilla is not maximum AI complexity.

It is coherent continuity.

The project repeatedly favors:

- persistent deterministic state over hidden LLM state
- exact source data over guessed data
- typed modules over one monolithic agent
- local/offline behavior over constant cloud dependency
- privacy abstraction over raw sensor exposure
- reusable libraries over regenerating everything
- genuine uncertainty over fake omniscience
- reflex/body behavior over forcing every event through conscious cognition
- character behavior over notification spam
- slow relationship change over instant emotional rewriting
- source provenance over destructive cleanup
- voice diversity over one flattened neutral model
- milestone-by-milestone playability over years of invisible infrastructure

This document intentionally stops before turning those ideas into priorities,
dependencies, milestones, or final technical decisions.
