## 1. Context and decision scope

[A00](DesktopRoomie-A00-A01-plan-v0.1.md#3-a00--prove-the-desktop-host) is a host-capability probe: establish a viable target for A01 through transparency, bounded pointer interaction, no unsolicited keyboard focus, layers/fullscreen coexistence, independent recovery and same-instance workspace placement. It is not the first playable companion. The original problem was whether a small body could safely coexist with ordinary work in the owner's Openbox/X11 session, rather than whether a universal desktop framework could be designed.

The plan requires comparing a second host only if the first fails a named requirement. The existing managed probe passed its qualified capability gates after reviewed corrections, including the Openbox off-workspace visibility amendment. The [M03 contract](DesktopRoomie-A00-M03-placement-recovery-host-selection.md) retained Rust/x11rb unless native evidence exposed a disqualifying limitation. No replacement or comparative research campaign is needed for this decision record. Historical failed candidates remain failures in the acceptance records; their successful corrections do not rewrite that history.

**Owner-ratified decision — 2026-10-23:** retain **Rust with x11rb and one borderless managed X11 UTILITY body**, procedural premultiplied-alpha rendering under Picom, SHAPE input regions, and ICCCM/EWMH cooperation with Openbox. Retain the existing pure-logic/native-resource/runtime boundaries and independent same-session CLI. The owner accepted this approach as satisfying original A00-G1/G2/G3 for the recorded target, subject to the documented scaling and native-host qualifications. Selection of this existing approach does not authorize redesign or alter implemented source boundaries.

## 3. Required host capabilities and configuration

The accepted deployment envelope is **Archcraft/Arch Linux, Openbox 3.6.1, X11 and Picom v13**. Those are tested versions, not a certification of all compatible/newer versions. [ENVIRONMENT](../experiments/desktop-probe/ENVIRONMENT.md) preserves dated configuration facts; [Openbox integration](host/OPENBOX.md) distinguishes required facilities from optional convenience configuration.

| Facility | Role and requirement |
| --- | --- |
| X11 connection and managed WM | Access to the owner's X server/screen, native windows/events/properties, selections and direct ClientMessages. Openbox must honor the exercised managed UTILITY, decoration, nonactivation, movement and state requests. The body uses `override_redirect=false`; the short-lived mouse popup alone uses override-redirect. |
| ICCCM | No-Input model (`WM_HINTS.input=false`, omitted `WM_TAKE_FOCUS`), `WM_DELETE_WINDOW`, coherent `WM_STATE`, checked current/all-desktop `WM_CHANGE_STATE` iconification. Keyboard isolation requires real typing evidence as well as hints. |
| EWMH | Advertised capabilities and readable `_NET_WM_STATE`/Above/Below/HIDDEN, body desktop, current desktop, desktop count and workarea; relevant state/desktop requests go to the WM. User time zero supports nonactivating local restore. Requests never directly overwrite WM-owned layer/desktop properties or switch `_NET_CURRENT_DESKTOP`. |
| RENDER and alpha visual | Query matching depth-32 picture formats with standard 8-bit ARGB channels (B/G/R/A shifts 0/8/16/24). The existing renderer generates premultiplied pixels, uploads a pixmap and blits the fixed 160×160 body; RENDER format discovery does not itself provide visible desktop compositing. Recorded RENDER version: 0.11. |
| Picom compositor | Running alpha compositing supplies transparent padding and blended translucent pixels without an opaque frame/rectangle. This is native visual evidence, not guaranteed solely by finding an alpha visual. Picom v13 is accepted; its exact backend/full config is not preserved here. |
| SHAPE input regions | SHAPE 1.1 input shaping separates interactive silhouette from visual alpha: empty padding passes input, the translucent patch remains interactive. Checked empty/restored shapes fence transitions; bounded post-map reassertion preserves the accepted silhouette. This is not a periodic reassertion policy. |
| RandR | Runtime requires RandR **1.5** monitor identities and subscriptions. Startup selects primary (first active if absent), then retains its name atom on refresh. Primary changes do not migrate the body; loss of the retained monitor is an error. |
| Destination model and fit | Usable area is selected-monitor/workarea intersection with checked arithmetic, wire range and whole-canvas fit. Here/Recover additionally require valid desktop count/current target, complete per-desktop workareas, absent-or-all-zero viewport, retained-monitor/body-size agreement and two complete agreeing reads. Sticky placement/nonzero viewport are unsupported there. Legacy readers remain distinct; only their absent-workarea case permits monitor-bounds fallback. |

The historical target uses click-to-focus and five desktops. Stage G exercised one eDP-2 at 1920×1080 +0+0; earlier named records include dual-monitor operation, which does not establish live hotplug or mixed-DPI support. No global key listener, tray manager, generic shortcut daemon or silent dotfile rewrite is introduced. Experimental wmctrl senders in historical host investigation are not runtime dependencies. ## 4. Why the managed host meets A00's needs

The same managed body provides native alpha and independently shaped input while delegating ordinary workspace, minimization and layer policy to Openbox. Position-only requests and fresh root-space geometry reconcile actual placement rather than bypassing the WM. Above/Normal/Below gives the manual foreground/background experiment; a covered body remains addressable through a separate control endpoint.

M01/M02 establish rendering, actual typing continuity, bounded dragging, release/cancellation and mouse-menu behavior. M03.1 records actual ordinary-window layers and natural Firefox fullscreen coverage/return. M03.2 provides managed Hide/Show and original-workspace Bring Top independently of body visibility. Public Stage D adds same-body workspace relocation; Stage E composes it with restoration/Above. RF preserves source ownership, Stage F strengthens deterministic joins, and Stage G accepts the integrated exercised behavior on the frozen executable. The [acceptance record](DesktopRoomie-A00-M03.4-integrated-acceptance.md) links the exact records rather than treating all of these as Stage G reruns.

The accepted fullscreen policy relies on Openbox naturally covering the Above body and returning it afterward; there is no fullscreen detector, active-window surveillance or re-raising loop. Stage G did not exercise fullscreen. During M03.4 planning **before C1**, the owner reported a supplemental fullscreen **PASS** for **2026-10-22**: it still worked as expected. Codex did not newly test fullscreen in C1, C2 or C3. No exact executable/binary identity, new logs, application/procedure details or independent verification were supplied for that report; its provenance remains separate from M03.1's native visual test and M03.2's qualified H25 evidence. Above confirmation never promises precedence over fullscreen.

This resolves the target-host selection problem at its documented capability scope without requiring a generic cross-platform abstraction, new renderer or further RF extraction. ## 5. Ownership, keyboard isolation and pointer safety

There is one managed body and one cooperative owner per X screen, discovered through a private selection and never-mapped InputOnly endpoint. Owner lifecycle is Starting/Ready/Closing, published independently of appearance delay. Delayed startup prevents accidental duplicate bodies and can reject early callers truthfully. The endpoint remains reachable while the body is minimized, unmapped or covered.

`ControlWindow.active` owns the sole active remote operation; `ProbeRuntime` owns the sole `LayerController`, pointer tracker, interaction, popup generation, movement and input fence. Local and remote adapters borrow these owners. Busy rejects competition instead of creating a queue or parallel controllers. Body-left explicit capture, opening-right automatic capture and popup explicit capture have distinct completion/release obligations; body and popup pointer ownership cannot coexist. Unknown acquisition or failed release retains cleanup debt. Popup selection settles checked release/destruction before layer dispatch; outside dismissal consumes its gesture.

No keyboard grab, SetInputFocus, activation request, global key listener or unexpected user-workspace switch is part of the host. No-input hints/user time zero cooperate with the WM; actual typing continuity in native acceptance establishes the exercised outcome. Transparent input and nonactivation remain separate from visible alpha. Transition fencing cancels stale gestures/movement, empties input and settles pointer/popup obligations before mutations. Safe re-enable needs fresh applicable visibility, placement and exact silhouette evidence. The optional universal startup input-disable refinement remains deferred; this record does not assert that native input is empty until Ready on every startup path.

Explicit resource release tracks Owned/Released/Unconfirmed outcomes. Shutdown cancels interaction, attempts pointer release before teardown and continues remaining cleanup after errors while preserving the original failure. Real X-server loss can only permit best-effort cleanup, not a guaranteed server acknowledgment. SIGKILL acceptance demonstrates server-side release/relaunch, not execution of application checked cleanup.

## 6. Remote control and bounded semantics

The CLI uses private protocol v2 on the same X server/screen: validated owner descriptor/epoch, immutable caller marker, one direct request and correlated terminal response. Here/Recover capture the caller's desktop through two strict reads **before owner discovery**, freeze it in the marker and revalidate before the single send. They do not retarget to a later workspace or the caller terminal's physical monitor. No-owner commands return without launching a body.

| Command | Verified postcondition / boundary | Owner / caller budget |
| --- | --- | --- |
| Hide | Genuine minimization, same body/workspace/layer, input safely fenced. | 1000 / 4000 ms |
| Show | Not minimized on original workspace, same effective layer. Local success needs safe placement/input; off-workspace success explicitly defers them. | 2500 / 4000 ms |
| Bring Top | Show if necessary, then exact Above on body's existing workspace; no relocation. | 3500 / 5000 ms; visibility cutoff 2500 ms from admission, layer ≤1000 ms capped by total |
| Bring Here | Same body on caller-frozen workspace, preserved effective layer and genuine minimization; minimized placement/input may remain deferred. | 3500 / 5000 ms |
| Recover | Here→Top in one active request; fresh frozen-workspace, local not-minimized, Above, fixed-size geometry and safe input proof. | 7000 / 9000 ms; Here ≤3500 ms, Top visibility ≤2500 ms from validated handoff, layer ≤1000 ms, all capped by original total |

Here uses at most one desktop request; Here/Recover permit at most one checked positional correction, with the full 150 ms confirmation interval. Recover handoff clears current proof while preserving identity, frozen layout/baseline, confirmed history and consumed/uncertain authority. It does not grant another correction or deadline. Partial requires a confirmed relocation and/or restoration transition appropriate to the command; no-op, correction and request acknowledgment do not suffice. An unconfirmed layer transition may leave Normal; there is no rollback or retry service.

The owner clears the active slot before at most one terminal reply attempt per admission. Caller timeout/reply loss gives OutcomeUnknown without resend or invented terminal outcome. This is not persistent global exactly-once deduplication: an identical post-completion request can be newly admitted under the accepted protocol. Same-session selection/markers protect cooperative identity and correlation, not security against arbitrary X clients.

Logical deadlines, no new mutation at cutoff, fresh final reads and bounded event batches prevent unbounded operation policy on a responsive server. Mandatory safety cleanup may continue after cutoff without renewing mutation authority. Synchronous X11 checks/replies have no independent hard transport timeout. The event loop services admitted requests before sleeping and waits on events/active deadlines; conditional held-button safety queries are not an idle polling service. Injected >64-event service/helper tests do not execute the complete native loop under every traffic interleaving.

## 7. Placement, visibility and layer verification

Request acknowledgment, event notification and successful final observation are different facts. Geometry uses actual root queries/translations rather than stale ConfigureNotify coordinates; local hit tests remain local. Strict placement reads agree on frozen destination/count/workarea/viewport/retained monitor and fit. Two matching snapshots are bounded evidence, not an atomic guarantee against an unobserved change-and-return. Changed/unreadable evidence cannot remain current success proof or authorize more mutation.

Visibility combines map state, ICCCM `WM_STATE`, EWMH HIDDEN, workspace and effective layer. On Openbox an ordinary off-workspace body can be **Iconic + Unmapped + no HIDDEN**; that is not genuine minimization. The accepted host adapter therefore retains local/current/all-desktop ICCCM Hide and local user-time-zero + one MapWindow Show, but uses WM-directed ADD-HIDDEN/REMOVE-HIDDEN elsewhere. Off-workspace Show sends neither MapWindow nor user-time write. These Openbox-observed HIDDEN requests are not assumed portable EWMH behavior for every WM and never directly write the state property.

Layer service validates advertised support and readable body flags: Above excludes Below, Below excludes Above, Normal has neither, and conflicting/unreadable states are not success. It requests at most an opposite-flag removal and target addition using the same pure controller, with fresh observation and a fixed deadline. It does not restore arbitrary relative peer order or fight WM policy. Show may allow Openbox's own local mapping policy to raise a Normal body; this is not an explicit DesktopRoomie Bring Top.

Minimized Here preserves minimization even on arrival; later explicit Show/Recover is needed to restore it. Off-workspace visibility success leaves input/placement deferred until an ordinary local return independently validates readiness. A late event may trigger a fresh read but cannot resurrect a completed operation, inherited proof, correction allowance or terminal obligation. Proven owner loss, native failure and clean Closing retain distinct classifications and original-error priority.

## 9. Limitations and consequences for A01

The target-qualified decision carries explicit limits: no certification of other WMs, Wayland or other platforms; no complete physical monitor hotplug/removal, forced workarea/viewport drift or X-server disconnection coverage; no reproduction of every refusal/malformed reply, Partial/OutcomeUnknown branch or scheduling interleaving. [Stage G's unexercised matrix](DesktopRoomie-A00-M03.3-stage-G-acceptance.md#5-limits-nonclaims-and-next-authority-gate) remains distinct from historical fullscreen/multi-monitor/Unknown observations and Stage F injected tests. Private control is not authenticated against hostile same-session clients, and synchronous reply stalls remain outside hard budget guarantees.

The host supplies proven technical drag, manual layers and explicit CLI placement/recovery; it does not supply A01 animation, autonomous/character movement, gravity, floor settings, persistence, user-versus-character layer policy, relative selected-window stacking or physical carrying across workspaces. Ordinary workspace changes cancel/suspend interaction instead of automatically following the user. The selected monitor remains fixed; unsupported geometry/identity changes fail safely rather than migrate by policy.

Once separately authorized, A01 can build on these existing pure/native/runtime boundaries and the accepted focus/pointer/geometry obligations. Its presentation, simulation, assets, settings and behavior need their own contracts and tests. A01 monitor-selection, workspace-placement and carrying/following policy decisions remain deferred; this ADR preserves current retained-monitor and explicit-command behavior without deciding those future policies. Keep reusable public code separate from private character content. Compatibility extensions or new host behavior require bounded review and host evidence; neither automatic research nor speculative refactoring is a prerequisite imposed by this ADR.

Reproduction uses the exact [build, diagnostic and control commands](DesktopRoomie-A00-M03.4-integrated-acceptance.md#6-reproducible-commands) in the companion acceptance record. Stable-toolchain builds are repeatable procedures, not a promise of byte-identical output. Optional desktop conveniences remain owner-controlled.
